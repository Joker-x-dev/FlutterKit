# 贡献指南

> 来源：[贡献指南](https://tdesign.tencent.com/flutter/getting-started)
> 归档时间：2026-10-30T16:00:00+08:00

感谢参与 TDesign Flutter。本文介绍本地开发、编码规范、问题反馈、Pull Request 提交和验收流程。

涉及公共 API、组件行为或跨目录改动时，请先阅读设计方案与验收记录规范，并随实现维护相应记录。

## 目录结构

```
tdesign-component/
├── demo_tool       // API 和演示代码
├── example         // 组件使用示例
├── lib             // 组件库
└── test            // 组件测试

tdesign-site/       // tdesign flutter 站点
```

## 本地开发

同时兼容 Flutter 3.32.0 与当前稳定版本。先安装目标 SDK，在仓库根目录执行：

```bash
cd tdesign-component
flutter pub get
cd example
flutter pub get
flutter run
```

在目标 Android/iOS 设备、模拟器或适用的 Web 环境运行。站点开发与右侧 Flutter Web 预览统一见站点开发说明，避免在此重复维护命令和端口配置。

## 开发规范

TD 内置视觉和行为只接受受支持的组件实例配置、TD ThemeExtension 与 Token；外部 Material/M2/M3 默认及显式主题不作为隐式入口。

- 组件命名规范：以 T 为前缀，组件名称、API 名称参考 TDesign 现有组件和 API 命名。
- 组件库用到的所有色值、圆角、字体字号等样式属性需全部定义在主题中。
- 代码规范遵循腾讯 Dart 代码规范。
- 对于系统原有组件（如 Text、Image 等），应兼容系统原组件功能，只能扩展，不能阉割。
- 示例页面尽量使用 ExamplePage + ExampleModule + ExampleItem 组合。
- 组件 API 和演示代码参考 demo_tool/README.md。
- 组件内部的固定文案抽离到 TResourceDelegate 统一管理。
- 如果已有 TDesign 组件封装，尽量使用现有 T 组件，而非直接使用系统组件。
- tdesign-component/CHANGELOG.md 由 CLI 自动生成，无需人工维护。

## PR 描述模板

提交 PR 时，正文必须完整保留 .github/PULL_REQUEST_TEMPLATE.md 的原模板结构，在此基础上只打勾 / 填写，不得删减模板本身的内容：

- 所有选项一律保留，选中的用 [x]，未选中的用 [ ]。
- 所有 HTML 注释一律保留，填写内容写在注释之后。
- 各小节标题与引导语保留。

## 领取 Issue

### 一个 Issue 的完整流程

1. 用户发现功能不满足，查看 API 文档确认不支持，然后提 Issue。
2. 提了 Issue 后，在群里发出 Issue 链接，确认详细需求，将结果贴到 GitHub 的 Issue 上。
3. 负责人评估开发工作量，打 help want 和 issueShoot 标签。
4. 贡献者确认要领取，在 Issue 下评论领取，并通知负责人。负责人打上 Received 标签，讨论确认实现方案。
5. 贡献者参考开发规范开发完功能，按照文档自检，然后提 PR，并同步负责人验收。
6. PR 自动构建测试包。
7. 负责人拉设计一起视觉走查，走查完成后合并 PR。Issue 打上下一个版本的标签。
8. 版本发布后，Issue 关闭。

### 标签管理

| 标签 | 含义 |
| --- | --- |
| 无标签 | 未评估 |
| issueShoot | 已评工作量，可领取 |
| Received | 已领取 |
| pre_x.x.x | 预计某个版本发布 |
| x.x.x | 某个版本已发布 |

## PR 关联 Issue

Issue 的主阵地是 GitHub。CNB 是镜像平台，其 Issue 与 GitHub Issue 是两套体系，因此：

- CNB 生成的 PR 不关联 CNB Issue（不写 Issue 编号，不写差异提示）
- Issue 关联在 GitHub 侧保留（close #xx 指向 GitHub Issue）

## PR 更新日志规范

PR 描述「更新日志」小节的目标受众是「用户」而非开发者，因此：

- **只记录用户可感知的变更**：仅当改动会改变用户在使用组件 / 库时能观察到的行为时才写入。
- **内部 / CI 改动不写日志**：纯内部实现、CI/CD 配置、文档结构调整不写入。
- **组件 PR 不单列 Demo 配套改动**：Demo 页面的改动应写在「需求背景和解决方案」中。
- **一个 PR 含多个功能 / 修复时，必须按条目分开列写**。

commit type 与分组对应关系：

| commit type | 最终分组 | 示例 |
| --- | --- | --- |
| breaking | Breaking Changes | breaking(toast): 调整 xxx 默认行为 |
| feat | Features | feat(TButton): 新增渐变背景能力 |
| fix | Bug Fixes | fix(TInput): 修复密文模式下无法粘贴的问题 |
| perf/refactor | Performance | refactor(toast): 优化 xxx |
| docs | Documentation | docs: 更新主题生成器文档 |
| 其他 | Others | chore: 升级依赖 |

## 示例代码片段


## 组件测试与 CI 回归门禁

新增组件测试时，需在 tdesign-component/tool/component_test_manifest.dart 中登记：

- componentTests：按组件执行并生成覆盖率的测试文件
- coverageTargets：纳入覆盖率统计的生产源码目录
- exampleTests：在 example 工程执行的共享功能测试
- visualTests：视觉回归 suite

登记后执行：

```bash
flutter test --no-pub test/tool
dart run tool/run_component_regression.dart
dart run tool/run_example_regression.dart
dart run tool/run_visual_regression.dart
```

## Spec 贡献流程

复杂需求、公共 API 变更、组件重构和跨目录改动，请按 specs/README.md 的完整流程创建并维护 Spec：

- 组件 Spec：specs/components/`<编号>-<组件分类>-<组件名>`/
- 非组件 Spec：specs/engineering/`<编号>-<类别>-<事项描述>`/

提交代码必须与 Spec 定义的行为契约 / 验收标准一致，方案变更时先更新 Spec 再改代码。

## 人工验收与合并

- 检查真实操作、布局溢出、明暗主题、英文环境、文字缩放和适用的焦点/键盘/无障碍能力。
- 在 Example App 检查对应 API 和代码查看入口。
- 视觉改动由负责人协调设计走查，并附目标、状态、平台与版本证据。
- Issue 验收完成后由负责人合并 PR；更新发布版本标签，正式发布后关闭对应 Issue。

## 文档维护

| 内容 | 唯一来源 | 使用与生成方式 |
| --- | --- | --- |
| 项目介绍和最短示例 | 根 README.md、README_zh_CN.md | 中英文分别维护，包内副本生成 |
| 安装、主题、国际化、FAQ、迁移 | tdesign-site/site/docs/ | 站点直接读取；包内 README 链接站点指南 |
| 贡献规范 | 本文件 | 站点直接读取并适配页面元信息 |
| API | lib 中的公开 dartdoc 注释 | 生成 example/assets/api，站点和示例 App 共用 |
| 示例 | example/lib 中的标注源码 | 生成 example/assets/code，站点和示例 App 共用 |
| 组件 FAQ | tdesign-site/docs/components/<组件>/README.md | 放在生成 API 入口后 |
| 设计决策与验收 | specs/ | 按组件或长期职责集中维护 |
